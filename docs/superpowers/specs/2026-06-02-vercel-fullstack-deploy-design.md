# Vercel Full-Stack Deploy Design

## Context

NorthStar is a pnpm monorepo with a React/Vite web app in `apps/web`, an Express API in `apps/server`, Drizzle/Postgres in `packages/db`, and AI/runtime packages under `packages/`. The root `vercel.json` already points toward a single full-stack Vercel deployment:

- `apps/web` builds static assets into `apps/web/dist/public`.
- `apps/server/api/index.ts` exports the Express app without starting `app.listen`.
- Root `api/[...path].js` loads the bundled server entry and lets Vercel route `/api/*` requests to it.
- Root rewrites send `/api/:path*` to `/api/[...path]`.

The current worktree contains many unrelated modified files, including environment files. This deployment work must not reset or rewrite those changes. Environment values are treated as secrets and must be configured through Vercel project settings or CLI env commands, not committed.

## Deployment Approach

Use one Vercel project rooted at the repository root.

This matches the codebase and minimizes moving parts. The web app and API share the same public origin, so browser requests can use relative `/api/...` URLs. That reduces CORS exposure, removes the need to coordinate two deployment URLs, and keeps preview deployments coherent: each preview gets its matching frontend and API from the same commit.

Rejected alternatives:

- Two Vercel projects: useful only if frontend and API need separate scaling or ownership. It adds CORS, duplicated env setup, and more deploy wiring.
- Vercel web plus API on another platform: useful for long-lived WebSocket or cron-heavy backends, but this repo already has a serverless Express adapter for request/response API traffic.

## Architecture

The deploy target is:

1. Vercel CDN serves the Vite static build from `apps/web/dist/public`.
2. Vercel rewrites `/api/*` to the root serverless function `api/[...path].js`.
3. `api/[...path].js` lazy-loads `apps/server/api/index.js`.
4. `apps/server/api/index.js` is generated by `apps/server/build.mjs` from `apps/server/api/index.ts`.
5. `apps/server/api/index.ts` imports and exports `apps/server/src/app.ts`.
6. `apps/server/src/index.ts` remains for local or non-serverless runtime only; Vercel must not use it because it starts HTTP, WebSocket, cron jobs, and registries.

WebSocket and scheduled/background work are out of scope for this single Vercel request/response deployment. API endpoints must still behave correctly when invoked as Vercel Functions.

## Database

Use an external Postgres provider reachable from Vercel, preferably Neon or another managed Postgres with `pgvector` enabled.

Required runtime variable:

- `DATABASE_URL`: runtime app role, DML-focused.

Required deploy/admin variable:

- `DATABASE_URL_MIGRATOR`: migrator role for `pnpm db:push`.

The canonical DB workflow remains `pnpm db:push`, because project rules state `db:generate` and `db:migrate` are legacy for the current baseline. Before deploy, the schema must be pushed with `DATABASE_URL_MIGRATOR`; runtime uses `DATABASE_URL`.

Readiness checks must pass:

- `/api/health/ready` returns `ok` or acceptable `degraded`.
- DB check passes.
- `pgvector` check passes.
- `discovery_sources` schema check passes.

## Runtime Services

Redis is optional unless rate limiting is configured fail-closed.

- If `RATE_LIMIT_REDIS_REQUIRED=true` or `REDIS_REQUIRED=true`, Vercel must have a public Redis URL such as `UPSTASH_REDIS_URL` or another `redis://` / `rediss://` endpoint reachable from Vercel.
- If Redis is not required, the API should still start and health should mark Redis as non-required.

AI, Stripe, Clerk, email, Sentry, push notifications, and external integrations are configured through env vars. The deployment can be considered structurally ready with only critical auth, DB, and app URL variables, but feature completeness requires the integration variables for enabled features.

## Environment Contract

Critical production variables:

- `NODE_ENV=production`
- `APP_URL=https://<vercel-domain>`
- `ALLOWED_ORIGINS=https://<vercel-domain>`
- `DATABASE_URL`
- `DATABASE_URL_MIGRATOR`
- `JWT_SECRET`
- `CLERK_SECRET_KEY`
- `VITE_CLERK_PUBLISHABLE_KEY`
- `IP_HASH_SALT`

Feature variables, depending on enabled surfaces:

- `AI_INTEGRATIONS_OPENAI_API_KEY`
- `AI_INTEGRATIONS_OPENAI_BASE_URL`
- `OPENROUTER_API_KEY`
- `OPENROUTER_BASE_URL`
- `STRIPE_SECRET_KEY`
- `STRIPE_WEBHOOK_SECRET`
- `STRIPE_TEAM_PRICE_ID`
- `RESEND_API_KEY`
- `RESEND_FROM_EMAIL`
- `SENTRY_DSN`
- `VITE_SENTRY_DSN`
- `SENTRY_AUTH_TOKEN`
- `SENTRY_ORG`
- `SENTRY_PROJECT`
- `VAPID_PUBLIC_KEY`
- `VAPID_PRIVATE_KEY`
- `VITE_VAPID_PUBLIC_KEY`
- `UPSTASH_REDIS_URL` or `REDIS_URL`

`VITE_API_URL` should not be required in production when the frontend calls same-origin `/api/*`. If any code still depends on it, the deployment should set `VITE_API_URL=/api` or the code should be adjusted to use relative URLs consistently.

## Build And Deploy Flow

The intended root build is:

```bash
pnpm install --frozen-lockfile
pnpm run typecheck
pnpm --filter @northstar/server exec node build.mjs
pnpm --filter @northstar/web run build
```

The deploy configuration should keep:

- root directory: repository root
- install command: `pnpm install --frozen-lockfile`
- output directory: `apps/web/dist/public`
- framework: Vite
- rewrite: `/api/:path*` to `/api/[...path]`

The server bundle generated at `apps/server/api/index.js` is ignored by git and rebuilt during deploy. Root `api/[...path].js` remains tracked as the Vercel function wrapper.

## Mobile And Desktop Verification

Verification must cover both static rendering and API-backed flows:

- `pnpm run typecheck`
- `pnpm --filter @northstar/server run test`
- `pnpm --filter @northstar/web run test`
- `pnpm --filter @northstar/server exec node build.mjs`
- `pnpm --filter @northstar/web run build`
- local preview or Vercel preview smoke check for `/`, `/api/health`, `/api/health/ready`
- Playwright desktop smoke on core pages
- Playwright mobile viewport smoke at 375px width

The deploy is not ready if any page has blocking render errors, API calls fail because of base URL configuration, or mobile navigation/layout blocks the core user path.

## Error Handling And Observability

The Express app already has a global error handler. For Vercel, failures must be surfaced through:

- `/api/health/live` for liveness.
- `/api/health/ready` for dependency readiness.
- Vercel function logs.
- Sentry when configured.

Production CORS must use explicit `ALLOWED_ORIGINS`, not `*`. Secrets must never be copied into committed files.

## Implementation Scope

Implementation should focus on deployment readiness:

- Validate Vercel config against the actual serverless entrypoints.
- Add or update deploy documentation and env checklist.
- Add missing smoke scripts if useful.
- Fix build/runtime issues discovered by local verification.
- Fix same-origin API configuration issues if any.
- Run desktop and mobile smoke tests before declaring readiness.

Do not refactor unrelated product code, rewrite existing dirty worktree changes, or move root agent context files.
